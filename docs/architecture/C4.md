# C4 Architecture

This document describes NeuroRoutine architecture with C4-style views.

## Level 1 - System Context

```mermaid
flowchart LR
  User[End User]
  App[NeuroRoutine SPA]
  Supabase[Supabase Platform\nAuth + Postgres + RLS]
  CI[GitHub Actions]
  Hosts[Vercel / Render]

  User --> App
  App --> Supabase
  CI --> Hosts
  Hosts --> User
```

## Level 2 - Container View

```mermaid
flowchart LR
  subgraph Browser[User Browser]
    SPA[React + TypeScript SPA]
    Cache[Local Storage + IndexedDB Queue]
  end

  subgraph Cloud[Backend Platform]
    Auth[Supabase Auth]
    DB[(Postgres + RLS)]
    Edge[Edge Functions]
  end

  SPA --> Auth
  SPA --> DB
  SPA --> Edge
  SPA --> Cache
```

## Level 3 - Component View (Frontend)

```mermaid
flowchart TB
  App[app/ Router + Bootstrap]
  Pages[pages/ Route composition]
  AuthF[features/auth]
  RoutinesF[features/routines]
  DashboardF[features/dashboard]
  Shared[shared/*]

  App --> Pages
  Pages --> AuthF
  Pages --> RoutinesF
  Pages --> DashboardF
  AuthF --> Shared
  RoutinesF --> Shared
  DashboardF --> Shared
```

## Level 4 - Code View (Routines Feature)

```mermaid
flowchart LR
  UI[Routine components]
  Store[routinesStore]
  Service[routinesService]
  API[supabase client]
  DB[(routines + routine_tasks + routine_task_events)]
  Offline[taskSyncQueue IndexedDB]

  UI --> Store
  Store --> Service
  Service --> API
  API --> DB
  Store --> Offline
```

## Notes

- Security boundary is the database via RLS, not only client-side guards.
- Offline queue reduces data loss risk during temporary disconnections.
- CI gates enforce minimum quality before deployment.
